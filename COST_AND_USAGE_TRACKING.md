# GeoViz — Cost & Usage Tracking

Last updated: 2026-05-12

This document covers the GeoViz audit cost model: where the tokens
go today, how we measure per-audit cost, the recommended target
cost per audit, and the staged path to a structured-JSON output
that decouples AI analysis from report presentation.

The intended reader is the operator running GeoViz, not the
customer. None of the content here is exposed publicly.

---

## 1. Current pipeline (what runs today)

Customer flow:

1. Stripe webhook flips a paid row to `reportStatus = "queued"`.
2. Railway-hosted worker (`scripts/geo-worker.ts`) polls, atomically
   claims one row, and calls the Anthropic API with a single
   `messages.create(...)` request.
3. The model returns a **full Markdown report** (~5–7 KB of prose:
   six rubric sections, three issues with body text, three fixes
   with body text, technical appendix). That markdown is the
   canonical artifact — persisted on `AuditOrder.reportMarkdown` and
   rendered by every customer surface and the PDF.
4. After the markdown save, two follow-ups fire (failure-isolated):
   the operator notification email and the
   `AuditIntelligence` row write (V2 data foundation — parsed
   structured signals from the markdown).
5. Operator reviews in `/admin/reports`, approves, sends. PDF is
   server-rendered from the same `/report/[id]/print` template.

### Pipeline trace (where tokens are spent)

| Step | Token source | Approx. count per audit |
|---|---|---|
| Prompt | `buildAuditPrompt(...)` in `scripts/geo-worker.ts` — **~1000 lines of priming, rubric framing, anchor scores, calibration notes, customer-tone instructions, section templates** | **~3,500–5,500 input tokens** |
| Tool round-trips | Server-hosted `web_search_20250305` tool fetches the homepage and `/robots.txt` (and sometimes sitemap.xml). Each fetched page is fed back into the model context. | **~2,000–6,000 additional input tokens** (varies with target-site page size) |
| Output | Generated markdown — six sections, prose-heavy, max-tokens capped at 8,000. Hits the cap on complex sites. | **~3,500–6,500 output tokens** |

A typical audit on **Claude Sonnet 4.5** ($3/M input, $15/M output):

```
input        ~5,000 × $3 / 1,000,000 = $0.0150
tool fetch  ~4,000 × $3 / 1,000,000 = $0.0120
output      ~5,000 × $15 / 1,000,000 = $0.0750
                                       --------
                                       ~$0.10 per audit
```

A complex-site audit (large homepage, multiple tool round-trips,
output near the 8k cap) lands closer to **$0.18 per audit**.

A retry (worker's `markFailureWithRetry` flips a transient-failure
row back to queued for up to 2 retries) **doubles or triples** the
billed cost for that order. Most retries are on `timeout` /
`fetch_failed` / `render_failed` — the first call still consumed
tokens before the timeout fired.

## 2. Cost drivers — ranked

These are the levers that actually move the needle, in priority
order:

### 2.1 The 1,000-line prompt (highest impact)

`buildAuditPrompt(...)` includes the entire rubric, anchor-score
ladder, calibration notes, customer-tone guidance, and section
templates **inline in every audit's input**. This is the dominant
fixed cost.

**Why it's there:** the prompt was tuned to be stable across
calibration runs and to give Claude enough context to score
consistently without prior fine-tuning. The trade-off was made
when scoring credibility was the priority. Now that the rubric is
frozen (per `CLAUDE.md` scoring-freeze block), this prompt is a
candidate for prompt-caching or pre-built JSON-schema extraction.

### 2.2 Tool-use round-trips

The `web_search` tool fetches the homepage + `/robots.txt`. Each
fetched page is round-tripped back into the model context as
additional input. Page size varies wildly — a small business homepage
might be 2k tokens; a heavy JS-rendered marketing site can exceed
8k tokens once readable text is extracted.

### 2.3 Markdown formatting in the output

The model spends ~30–40% of its output budget on **formatting
overhead**: section headers, bullet markers, divider rules,
"Why this band:" framing prose, repeated category-name labels,
checkmark / cross markers, dollar-amount placeholders. None of
that needs to be generated by Claude — the React renderer can
produce it from a small structured payload.

### 2.4 Long prose explanations

Each rubric category gets a paragraph-length "why this score"
explanation. Each of the three top issues gets a body paragraph.
Each of the three top fixes gets a body paragraph plus
What-To-Do / Why-It-Matters / Expected-Impact labeled fields. This
is ~2,500 output tokens of human-readable prose. Most of it is
re-paraphrasing the same structural findings.

### 2.5 Retries (transient failures × 2)

`processing-status.ts` allows up to 2 auto-retries on transient
failures. Each retry consumes a fresh API call — the first attempt
already consumed tokens before timing out, so the worst case is
**3× the token cost on a flapping target**. The cap is intentional
(prevents infinite loops), but should be monitored.

## 3. Per-audit cost tracking (Phase 1 — now live)

This pass adds **visibility only** — no behavior change to the
worker, the prompt, or the markdown pipeline.

### What's captured

After each successful Anthropic API call, the worker captures
`response.usage` and persists six new columns on `AuditOrder`:

| Column | Source |
|---|---|
| `inputTokens` | `response.usage.input_tokens` |
| `outputTokens` | `response.usage.output_tokens` |
| `cacheCreationTokens` | `response.usage.cache_creation_input_tokens` |
| `cacheReadTokens` | `response.usage.cache_read_input_tokens` |
| `modelUsed` | the model ID used for the call (e.g. `claude-sonnet-4-6`) |
| `estimatedCostUsd` | computed via `src/lib/pricing.ts` at decimal(10, 6) precision |

### Where it lives

| Surface | Output |
|---|---|
| **Worker log line** | `[geo-worker] api usage input=3812 output=4271 cacheCreate=0 cacheRead=0 model=sonnet cost=$0.0769` |
| **`AuditOrder` row** | Six new columns above. Queryable via Prisma. |
| **CLI mode** | No usage captured (the Claude CLI doesn't expose token counts). All six columns stay `NULL`. |

### Querying cost data

Per-audit cost (last 50):

```ts
await prisma.auditOrder.findMany({
  where: { estimatedCostUsd: { not: null } },
  orderBy: { reportGeneratedAt: "desc" },
  take: 50,
  select: {
    id: true,
    websiteUrl: true,
    modelUsed: true,
    inputTokens: true,
    outputTokens: true,
    estimatedCostUsd: true,
    reportGeneratedAt: true,
  },
});
```

Aggregate spend over a window:

```ts
await prisma.auditOrder.aggregate({
  where: {
    estimatedCostUsd: { not: null },
    reportGeneratedAt: { gte: new Date(Date.now() - 30 * 24 * 3600 * 1000) },
  },
  _sum: { estimatedCostUsd: true, inputTokens: true, outputTokens: true },
  _count: { _all: true },
  _avg: { estimatedCostUsd: true },
});
```

### How to calculate cost per report (formula)

```
estimatedCostUsd
  = (inputTokens         × inputRate         / 1_000_000)
  + (outputTokens        × outputRate        / 1_000_000)
  + (cacheCreationTokens × cacheCreationRate / 1_000_000)
  + (cacheReadTokens     × cacheReadRate     / 1_000_000)
```

Rates per model family (USD per 1M tokens — verify against the
live Anthropic billing dashboard before treating as financial
truth):

| Family | Input | Output | Cache create | Cache read |
|---|---|---|---|---|
| Haiku | $1.00 | $5.00 | $1.25 | $0.10 |
| **Sonnet (default)** | $3.00 | $15.00 | $3.75 | $0.30 |
| Opus | $15.00 | $75.00 | $18.75 | $1.50 |

The rate table lives in `src/lib/pricing.ts`. Update it there when
Anthropic publishes new pricing; the per-audit Decimal column
records the rates that were active at the time of the call (via
`modelUsed`) so historic costs stay correct.

## 4. Recommended target cost per audit

| Tier | Target | What it implies |
|---|---|---|
| **Today** | $0.10–0.18 / audit | Full prose markdown, no caching, no JSON path |
| **Phase 2 target** | **$0.03–0.06 / audit** | Structured JSON output + prompt caching |
| **Phase 3 stretch** | $0.02 / audit | + Haiku for low-complexity audits + cached system prompt |

The Phase 2 target assumes:
- ~70% reduction in output tokens (JSON ~1,500 tokens vs 5,000+ markdown)
- ~40% reduction in effective input cost (prompt caching on the
  fixed rubric block; per-audit only pays cache-read rate)
- Continued use of Sonnet for scoring quality

## 5. Migration path — structured JSON output

This is the **next-step recommendation**, not part of this pass. The
goal is to separate AI analysis (Claude's job) from report
presentation (the renderer's job).

### Phase 2A — introduce JSON output path (non-breaking)

1. Add a new prompt builder `buildAuditPromptJson(...)` that asks
   Claude to return a single JSON object matching this shape:
   ```ts
   type AuditPayload = {
     businessName: string;
     websiteUrl: string;
     overallScore: number;
     scoreBand: "weak" | "needs_improvement" | "strong" | "excellent";
     categoryScores: {
       structuredIdentity: { score: number; max: number };
       crawlerAccessibility: { score: number; max: number };
       trustSignals: { score: number; max: number };
       contentDepth: { score: number; max: number };
       brandClarity: { score: number; max: number };
       technicalAccessibility: { score: number; max: number };
     };
     topIssues: Array<{ title: string; severity: "critical" | "high" | "quick_win" | "trust"; body: string }>;
     topFixes: Array<{ title: string; priority: "P0" | "P1" | "P2"; difficulty: "easy" | "moderate" | "technical"; body: string }>;
     strengths: string[];
     trustSignals: {
       reviewsDetected: boolean;
       napConsistency: boolean;
       certifications: string[];
     };
     crawlabilityFindings: {
       robotsTxtAllows: boolean;
       blockedBots: string[];
       sitemapPresent: boolean;
     };
     schemaFindings: {
       hasLocalBusiness: boolean;
       hasFaq: boolean;
       hasReview: boolean;
     };
     recommendationReadiness: {
       overall: "weak" | "moderate" | "strong";
       perPlatform: { chatgpt: number; claude: number; gemini: number; perplexity: number };
     };
     executiveSummaryShort: string;     // one-line, ≤ 180 chars
     operatorNotes: string | null;       // optional, calibration hints
     confidenceLevel: "low" | "medium" | "high";
   };
   ```
2. Add `auditPayload Json?` column to `AuditOrder` (or
   `AuditIntelligence` — TBD).
3. Worker writes BOTH `reportMarkdown` AND `auditPayload` initially
   — the new path is **shadow** mode. No customer impact.
4. New renderer component `AuditReportFromJson` reads from the
   payload. Existing `AuditReportContent` (markdown-based) stays
   the canonical surface.
5. Validate the JSON path on the calibration cohort (78 backfilled
   rows + new test runs). Compare scores, prose quality, and PDF
   fidelity.

### Phase 2B — flip new audits to JSON-only

Once the JSON path is validated:

1. Set a feature flag (`GEO_AUDIT_OUTPUT = "json"` env). New audits
   skip markdown generation entirely — Claude returns ~1,500 tokens
   of structured data, the renderer assembles the report.
2. Markdown column stays nullable; historic audits continue
   rendering from markdown. No backfill required.
3. PDF rendering uses the same renderer path (server-side
   `/report/[id]/print` is unchanged — it just reads from a different
   data source).

### Phase 2C — prompt caching

The first 3,500–5,500 tokens of the rubric / framing prompt are
**identical** across every audit. Anthropic prompt caching lets us
mark that block cacheable; subsequent audits pay the cache-read
rate (10% of input) for that prefix instead of full input rate.

Expected savings: 30–40% of input cost — most of which is the
fixed prompt overhead today.

### Phase 2D — model tiering

After Phase 2A/B is stable, route low-complexity audits (small
single-location businesses, simple sites) to **Haiku** instead of
Sonnet. Worker decides at queue time based on a quick page-size
check. Sonnet stays the default for everything else.

Expected savings: 50–60% on the audits that get downgraded
(typically ~30% of volume).

### What NOT to do

- Don't change the rubric weights or band thresholds (frozen per
  `CLAUDE.md`).
- Don't reduce report quality to chase token savings — the audit
  is the product, not a loss-leader.
- Don't break existing audits or PDF rendering — markdown stays
  supported until JSON is proven on real customer flow.
- Don't enable prompt caching before measuring cache hit rate —
  with web search tool turned on the cache invalidates per-request,
  so caching might not help in the current shape.

## 6. Health checks (what to watch)

After this pass deploys, watch these in Railway / Prisma:

- **`estimatedCostUsd` distribution.** A long tail above $0.20 means
  audits are hitting max_tokens. Investigate prompt drift or
  unusually large target sites.
- **`retryCount > 0` rate.** Currently bounded at 2 retries per
  audit. If many audits use retry slots, you're paying 2–3× per
  affected order. Look at `failureReason` to find the dominant
  transient cause.
- **`cacheReadTokens > 0` percentage.** Today this should be 0% —
  prompt caching isn't enabled. Watch when Phase 2C ships.
- **30-day rolling spend** via the aggregate query above. Set a
  weekly alarm if total > $X for current customer volume.

## 8. Phase 1.5 — operator visibility surfaces

Phase 1 captured the data. Phase 1.5 surfaces it where the operator works.

### 8.1 Where cost data appears now

| Surface | What you see | When |
|---|---|---|
| **`AuditOrder` columns** | `inputTokens`, `outputTokens`, `cacheCreationTokens`, `cacheReadTokens`, `modelUsed`, `estimatedCostUsd`, `workerRuntimeMs` | Persisted on every API-mode audit completion. CLI-mode runs leave these NULL. |
| **`[geo-cost]` log line** (NEW) | One line per audit, written at completion: `[geo-cost] auditId=… model=… input=… output=… cost=$… runtime=…ms url=… status=generated retries=…`. Failed audits emit a matching line with `status=<failed\|retried> reason=<failureReason>`. | Every audit, success or fail. Tail Railway logs with `grep '\[geo-cost\]'` to get a single line per audit, no scrolling through the broader `[geo-worker]` chatter. |
| **Admin queue UI** (NEW) | Each card in `/admin/reports` has an `Audit Cost & Runtime (internal)` collapsed `<details>` block. Shows estimated cost, model, input/output tokens, runtime, retry count, status, and failure reason when applicable. | Admin-only — page is gated by `validateAdminAccess` (ADMIN_SECRET). Block is rendered in the admin card, never reaches `AuditReportContent` or any customer route. |
| **`npm run intelligence:cost`** (NEW) | Aggregate summary script — last 30 days by default. Shows: total spend, avg cost, retried-audit count, failed-audit count by reason, top-5 most expensive audits, distribution by model. Flags: `--days=N`, `--limit=N`. | Run from local terminal whenever you want a roll-up. Read-only; safe against production. |

### 8.2 How estimated cost is calculated

Already covered in §3 of this doc — the worker computes `estimatedCostUsd` via `estimateAuditCostUsd(modelId, usage)` from `src/lib/pricing.ts`, persists it as Decimal(10,6), and writes the model ID alongside so historic cost values stay correct across model upgrades.

The admin UI and the cost-summary script both read the persisted value (no re-computation, no drift).

### 8.3 What may still be missing

- **CLI-mode audits have no usage data.** The Claude CLI doesn't expose token counts in the wrapper's output, so when `GEO_AUDIT_MODE=cli`, the six cost columns stay NULL. The admin block reads "Cost data unavailable for this audit (CLI mode or pre-telemetry row)." Production should always be `api` mode; CLI is a dev fallback.
- **Pre-Phase-1 historic rows have no usage data.** Same treatment — admin block reads as unavailable. No backfill (the SDK doesn't expose retroactive usage for past calls).
- **Token spend before a failed audit's failure is logged but not persisted.** When an audit fails mid-response (timeout, fetch failure, etc.), Anthropic still bills for the tokens consumed up to that point. The worker emits a `[geo-cost]` line with `status=<failed|retried>` so you can see it in logs, but the failed row's cost columns are left NULL — there's no clean SDK surface for "partial usage on a failed call" today. Treat the log line as the source of truth for failure-attempt cost.
- **PDF generation time is not persisted.** PDFs are on-demand at `/api/report/[id]/pdf` — a single audit could be downloaded N times. Per-PDF runtime is logged in the PDF route but not attached to the audit row.
- **The `web_search` tool's internal accounting** may diverge slightly from the SDK's `input_tokens` field. See §8.4 for reconciliation.
- **Prompt caching is not yet active.** `cacheCreationTokens` and `cacheReadTokens` are wired up in the column set but always show 0 today. They'll start populating when Phase 2C lands.

### 8.4 How to reconcile with Anthropic Console

Treat the persisted `estimatedCostUsd` as a **directional budgeting signal**, not the source of truth for billing.

Expected sources of small (~5%) per-row mismatch vs. the Console:

- **Tool-use round-trip accounting.** The `web_search` server tool round-trips homepage / robots.txt content back into the model context. The SDK's `input_tokens` field includes the round-trip input, but the exact accounting for hosted tools may evolve between SDK versions.
- **Cache-creation premium.** Anthropic's published rate is 25% over input. The pricing table uses 25% × the family rate. Actual billed cache-creation cost may be precise to a fraction we don't model.
- **Time-of-call rate.** The pricing table is hardcoded in `src/lib/pricing.ts`. If Anthropic publishes new rates AND you haven't updated the table, persisted cost will be wrong for new audits until the table is updated. The `modelUsed` column records the model ID, so historic cost can be re-computed offline by re-running `estimateAuditCostUsd(modelUsed, usage)` with corrected rates if needed.

**Reconciliation cadence:** at month-end, compare:
- `npm run intelligence:cost -- --days=30` → total spend
- Anthropic Console → monthly billed spend

A persistent >10% gap signals either the rate table is stale, the SDK usage shape changed, or many failed-mid-response audits aren't being captured. Investigate before letting it drift further.

### 8.5 V2 improvements

- **Prompt-caching capture and reporting.** Once Phase 2C ships, `cacheReadTokens` will start populating and the cost-summary script should grow a "cache savings" line showing what % of input cost was offset by hits.
- **Per-tool-call breakdown.** If/when the Anthropic SDK exposes per-tool token attribution, persist it alongside the existing columns so we can see which tools dominate the input cost (likely `web_search`).
- **Failed-audit token cost persistence.** Once the SDK exposes partial-usage data on failures (or we implement client-side estimation), populate the cost columns on failed rows too. Today they stay NULL.
- **Cost-by-industry slice.** The `AuditIntelligence.industryCategoryNormalized` column already exists. Add a `groupBy` over the join to surface per-industry cost averages — useful for routing decisions (e.g., "this industry consistently fits Haiku").
- **Haiku-routing decision telemetry.** When Phase 2D ships, log the routing decision per audit so the cost-summary script can show "Sonnet vs Haiku" cohort comparisons and validate the savings.
- **Failure-cost log scraper.** A small offline script that scrapes the `[geo-cost]` failure lines from Railway logs and writes them back to a `FailedAttemptCost` table — gives a queryable view of pre-failure token spend until partial-usage SDK support lands.
